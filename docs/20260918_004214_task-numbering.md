# Task Numbering — Implementation and Verification

## Summary and approved scope

Derek approved adding human-readable task numbers, then selected `#1`, `#2`,
`#3`, ... instead of a padded prefix. Numbers are unique and increasing across
workspaces in one database. UUIDs remain the internal identities. Tasks retain
numbers after completion, cancellation, reopening, retries and restarts.
Independent databases and restored/divergent histories are not a global sequence.

The approved work is limited to storage migration, four-tool compatibility,
usage documentation, tests, local plugin upgrade and publishing the repository.
No Godot task execution or task-content change is included.

## Implementation

- `task_management/store.py`: schema 2 adds an AUTOINCREMENT number-to-UUID
  mapping. New task, number, dependencies and creation event commit together.
- Existing schema 1 gets a private SQLite backup while the migration holds the
  writer lock. A separate read connection takes the backup. Creation-event
  sequence supplies the old tasks' actual order, even for identical timestamps.
  Missing creation events abort the migration. Task/dependency/event rows remain
  unchanged; historical JSON is not rewritten and task revisions do not advance.
- `task_number` is returned as a string such as `"#1"`. `task_get` and
  `task_update` resolve it within the supplied workspace before using the UUID
  for revision checks, history cursors and mutations. Original UUID calls and
  pagination ordering remain supported. Dependency arrays still use UUIDs to
  preserve saved idempotency payloads; resolve numbers through `task_get` first.
- `task_management/server.py`, README and the usage skill describe number-based
  references. No new tool or third-party dependency is introduced.

## Tests and review

Baseline: all 24 existing tests passed. RED: eight new numbering tests failed
against the original implementation, and the MCP lifecycle failed because the
response lacked `task_number`. GREEN: all 34 tests passed, including ten new
numbering/migration tests and expanded legacy/automatic MCP transport checks.

Coverage includes cross-workspace numbering and isolation, immutable numbers,
idempotent retry, stale revisions, UUID/number cursor interchange, signed-64-bit
input bounds, six competing creators, three competing migrators/retries, event
failure rollback, backup failure, missing-history migration rollback, backup
writer locking, unchanged raw v1 rows, and unchanged historical snapshots.

An independent read-only review found no implementation blocker. All four plan
findings were accepted: lock before backup, bound numeric inputs, canonicalize
UUID before cursor/query use, and verify the newly installed host rather than
assuming reinstall replaces an already-running server. A separate real stdio
probe kept the previous installed v1 server alive across migration and verified
that both its subsequent read and attempted write returned `unsupported_schema`,
with the original task unchanged. Plugin and skill validators passed.

## Deployment and recovery

The source lives at `~/GitHub/task-management`; `~/plugins/task-management` is
its compatibility symlink for the personal marketplace. Reinstall uses the
official cachebuster helper and `task-management@personal` command, without
manual marketplace edits.

Schema 1 backups are placed beside the database with the pattern
`<database>.schema1.<UTC timestamp>.<unique suffix>.sqlite3`. Keep this backup;
there is no automatic downgrade. Existing MCP processes reject schema 2 and
need a new thread/reconnection to load the updated plugin. Restoring an older
backup requires accounting for any subsequent task writes and numbering.

Installation and live-data acceptance results will be recorded after deployment.
